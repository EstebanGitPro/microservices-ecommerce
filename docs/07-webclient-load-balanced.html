Comunicación dinámica con WebClient y @LoadBalanced

Cómo order-service dejó de llamar a localhost:8082 y pasó a llamar a inventory-service por nombre, repartiendo las llamadas entre varias instancias registradas en Eureka.

Antes de seguir: la config actual tiene un bug En WebClientConf la URL base es http://INVENTORY-SERICE (falta la V). Eureka no tiene ningún servicio con ese nombre, así que el load balancer no encuentra instancias y la llamada falla. Tiene que ser http://INVENTORY-SERVICE, el spring.application.name de inventory. Eureka no distingue mayúsculas, así que inventory-service también sirve. Al final, en la sección 7, hay otros detalles para corregir.

1. El problema: un número de teléfono fijo

Imaginá que querés pedir una pizza y siempre llamás al celular de Juan, un empleado de la pizzería. ¿Qué pasa si Juan está ocupado, se fue a su casa o cambió de número? Te quedás sin pizza. Lo mejor es llamar a "la pizzería": atiende una recepcionista que sabe qué empleados están trabajando y te pasa con uno libre.

Lo técnico

ANTES: dirección fija 
@Bean
public WebClient webClientBuilder() {
  return WebClient.builder()
      .baseUrl("http://localhost:8082")
      .build();
}

Una sola máquina y un solo puerto. Si levantás una segunda instancia de inventory, nunca recibe tráfico. Si la del 8082 se cae, se cortan todas las órdenes.

AHORA: nombre lógico 
@Bean
@LoadBalanced
public WebClient.Builder webClientBuilder() {
  return WebClient.builder();
}

// ...
builder.baseUrl("http://INVENTORY-SERVICE").build();

INVENTORY-SERVICE no es un host de verdad: es el nombre del servicio en Eureka. En cada request se traduce a la IP y el puerto de una instancia viva.

Para lograrlo hicieron falta tres piezas, que se explican una por una abajo:

  1. Exponer un WebClient.Builder en lugar de un WebClient ya construido (sección 2).
  2. Tener Spring Cloud LoadBalancer en el classpath (sección 3).
  3. Marcar ese builder con @LoadBalanced (sección 4).

2. Qué es un Builder

Un builder es como armar una hamburguesa en un local donde vos elegís todo. Primero decís "pan", después "carne", después "queso", después "sin cebolla". Mientras elegís, la hamburguesa todavía no existe: solo hay una lista de instrucciones. Cuando decís "¡listo, armala!" te entregan la hamburguesa terminada, y esa ya no se cambia. Si querés otra distinta, pedís otra.

Lo técnico

Builder es un patrón de diseño creacional: separa cómo se configura un objeto de el objeto final. Sirve cuando el objeto tiene muchas opciones (URL base, headers, filtros, codecs, timeouts) y un constructor con diez parámetros sería imposible de leer.

WebClient client = WebClient.builder()          // 1. empezás a pedir
    .baseUrl("http://INVENTORY-SERVICE")         // 2. cada método configura y devuelve el mismo builder
    .defaultHeader("X-Source", "order-service")
    .filter(miFiltro)
    .build();                                    // 3. "armala": devuelve un WebClient inmutable

¿Por qué el bean ahora es el Builder y no el WebClient?

Porque @LoadBalanced trabaja sobre el builder. Spring le agrega un filtro antes de que llames a build(). Si el bean fuera un WebClient ya construido, ya no habría forma de meterle ese filtro. Es como querer agregarle queso a la hamburguesa cuando ya está envuelta: hay que hacerlo mientras se arma.

Ojo: el builder es mutable y es un singleton Tu bean WebClient.Builder es uno solo para toda la aplicación. Cuando invetoryClient(builder) hace builder.baseUrl(...), modifica ese builder compartido. Si mañana otro bean lo usa para llamar a product-service, hereda la baseUrl de inventory. La solución es clonarlo: builder.clone().baseUrl("http://INVENTORY-SERVICE").build(). clone() copia la configuración, incluido el filtro de load balancing.

3. La dependencia spring-cloud-starter-loadbalancer

El load balancer es la recepcionista de la pizzería. Tiene la lista de empleados que vinieron hoy (se la da Eureka) y reparte los pedidos por turnos: el primero a Juan, el segundo a Ana, el tercero a Luis, el cuarto otra vez a Juan... Así nadie se queda sin hacer nada y nadie trabaja el doble.

Lo técnico

<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-starter-loadbalancer</artifactId>
</dependency>

Trae Spring Cloud LoadBalancer, el balanceador del lado del cliente. "Del lado del cliente" quiere decir que la decisión de a qué instancia llamar la toma order-service, no un proxy externo como Nginx. Tiene tres piezas:

  • ServiceInstanceListSupplier: consigue la lista de instancias de un servicio. Como el proyecto usa Eureka, se la pide al DiscoveryClient de Eureka (y la guarda en caché un rato).
  • ReactiveLoadBalancer: elige una instancia de esa lista. Por defecto es RoundRobinLoadBalancer (por turnos). También existe RandomLoadBalancer.
  • Los adaptadores HTTP: el filtro que @LoadBalanced conecta a WebClient, a RestClient o a RestTemplate.
Dato: la dependencia ya venía incluida spring-cloud-starter-netflix-eureka-client (5.0.3, el que ya está en order-service/pom.xml) trae spring-cloud-starter-loadbalancer como dependencia transitiva con scope compile. Declararla de forma explícita no rompe nada y deja clara la intención ("este servicio balancea"), pero no es lo que hizo que funcione. El api-gateway también la declara: usa el mismo mecanismo con las URIs lb://PRODUCT-SERVICE.

4. La anotación @LoadBalanced

Tenés varios teléfonos en tu casa. A uno le pegás un sticker que dice "pasa por la recepcionista". Cuando marcás "la pizzería" desde ese teléfono, la llamada va primero a la recepcionista, que te conecta con un empleado. Desde un teléfono sin sticker, marcar "la pizzería" no funciona: no es un número de verdad.

Lo técnico

@LoadBalanced es, literalmente, un @Qualifier: una marca sobre un bean. No hace nada por sí sola. Lo que la hace funcionar es esto:

  1. Al arrancar, Spring Cloud registra un BeanPostProcessor (LoadBalancerWebClientBuilderBeanPostProcessor).
  2. Ese post-processor busca los beans WebClient.Builder que tengan la marca @LoadBalanced.
  3. A cada uno le agrega un ExchangeFilterFunction de load balancing. Es un filtro que se ejecuta en cada request, antes de salir a la red.
  4. En cada request, el filtro toma el host de la URL (INVENTORY-SERVICE) como serviceId, le pide una instancia al load balancer y reescribe la URL con la IP y el puerto reales.

Paso a paso de una llamada

inventoryClient.reduceInventory("SKU-1", 3)Lo llama OrderServiceImpl, igual que antes

¿Qué pasa sin la anotación?

El WebClient intenta resolver INVENTORY-SERVICE por DNS, como si fuera google.com. No existe, y obtenés un WebClientRequestException causado por UnknownHostException. En tu código cae en el catch y se muestra como "No se pudo contactar al servicio de inventario".

@LoadBalanced sobre el bean InvetoryClient no hace nada El post-processor solo mira beans de tipo WebClient.Builder, RestClient.Builder y RestTemplate. En invetoryClient(...) la anotación queda como un qualifier suelto que nadie usa. No rompe nada, pero confunde: parece que hace falta y no hace falta. El balanceo ya viene en el builder que recibís como parámetro.

5. Levantar varias instancias de inventory-service

En el súper hay tres cajas abiertas. Cada caja necesita su propio número ("caja 1", "caja 2", "caja 3"); si todas dijeran "caja 1", nadie sabría a cuál ir. Y cada cajero necesita su propio cartelito con su nombre; si los tres se llamaran igual en la lista del gerente, el gerente pensaría que hay uno solo. El número de caja es el puerto. El cartelito es el instance-id.

Lo técnico: configuración en IntelliJ

  1. Abrí Run → Edit Configurations… y elegí la configuración de InventoryServiceApplication.
  2. Modify options → Allow multiple instances. Sin esto, si apretás Run otra vez, IntelliJ detiene la instancia que está corriendo en lugar de levantar otra.
  3. Modify options → Add VM options, y en el campo VM options poné:
-Dserver.port=0 -Deureka.instance.instance-id=${spring.application.name}:${random.uuid}
  1. Dale Run dos o tres veces. Cada ejecución es una instancia nueva.

-D: qué significa

-Dclave=valor define una system property de la JVM. Spring Boot las lee como propiedades, y tienen más prioridad que application.yaml. Por eso -Dserver.port=0 le gana al server.port: 8082 del yaml sin tocar el archivo.

-Dserver.port=0

El puerto 0 es especial: le dice a Spring Boot "pedile al sistema operativo cualquier puerto libre". Cada instancia arranca en un puerto distinto (por ejemplo 54012, 54088, 54131) y nunca chocan con Port 8082 was already in use. Que el puerto sea al azar no es problema, porque nadie llama a inventory por puerto: lo encuentran a través de Eureka. Cuando el servidor termina de arrancar, el cliente de Eureka registra el puerto real, no el 0.

-Deureka.instance.instance-id=${spring.application.name}:${random.uuid}

El instance-id es el identificador único de cada instancia dentro de Eureka. Si no lo configurás, Spring Cloud lo arma así:

${spring.cloud.client.hostname}:${spring.application.name}:${spring.application.instance_id:${server.port}}

Con server.port=0, las tres instancias terminan con el mismo ID:

MacBook-Pro.local:inventory-service:0   ← instancia 1
MacBook-Pro.local:inventory-service:0   ← instancia 2 (pisa a la 1)
MacBook-Pro.local:inventory-service:0   ← instancia 3 (pisa a la 2)

Eureka cree que son la misma instancia que se re-registra. En el dashboard ves una sola y el load balancer solo conoce una. Con la propiedad, cada una tiene un ID propio:

inventory-service:3f2a9c1e-8b7d-4e21-9a0f-6c55d2e1b7a4
inventory-service:a81c04d2-1f3e-4b9a-8e6d-2d7f9b0c3e15
inventory-service:5d9e7b30-c2a4-4f18-b6e1-9a3c8f2d0e77
  • ${spring.application.name} es un placeholder: Spring lo reemplaza por inventory-service.
  • ${random.uuid} lo resuelve RandomValuePropertySource de Spring Boot, que genera un UUID nuevo en cada arranque. También existen ${random.int}, ${random.long} y ${random.value}.

6. Cómo comprobar que funciona

  1. Levantá config-server, discovery-server, tres instancias de inventory-service y order-service.
  2. Abrí http://localhost:8761. En INVENTORY-SERVICE tienen que aparecer 3 instancias en estado UP.
  3. Creá varias órdenes seguidas y mirá la consola de cada instancia de inventory: los requests de /reduce se van alternando entre ellas.
  4. Apagá una instancia y seguí creando órdenes. Puede que alguna falle durante unos segundos, hasta que Eureka y la caché del load balancer se enteren de que la instancia cayó. Después, el tráfico se reparte entre las dos que quedan.

7. Qué falta corregir en WebClientConf

  1. Typo en la URL: INVENTORY-SERICE → INVENTORY-SERVICE. Es el que rompe la comunicación hoy.
  2. Sacar @LoadBalanced del bean invetoryClient: no tiene efecto ahí (sección 4).
  3. Usar builder.clone() antes de baseUrl(...) para no modificar el builder compartido (sección 2).
@Bean
@LoadBalanced
public WebClient.Builder webClientBuilder() {
    return WebClient.builder();
}

@Bean
public InvetoryClient invetoryClient(WebClient.Builder builder) {
    WebClient webClient = builder.clone()
            .baseUrl("http://INVENTORY-SERVICE")
            .build();

    HttpServiceProxyFactory factory = HttpServiceProxyFactory
            .builderFor(WebClientAdapter.create(webClient))
            .build();

    return factory.createClient(InvetoryClient.class);
}
La lección order-service ya no sabe dónde está inventory, solo cómo se llama. La dirección real la resuelven Eureka (quién está vivo) y el load balancer (a cuál le toca), en el momento de cada request. Por eso podés agregar o quitar instancias sin tocar ni redeployar order-service.
