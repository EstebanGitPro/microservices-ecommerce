Cliente HTTP de inventory-service

Por qué el código con webClientBuilder.build().put()... quedó comentado en OrderServiceImpl, y qué lo reemplazó.

Corrección importante antes de empezar WebClient no dejó de usarse. WebClientConf sigue activa y cada llamada a inventory sigue viajando por un WebClient. Lo que cambió es quién lo usa: antes lo usaba tu service a mano; ahora lo usa un proxy que Spring genera a partir de la interfaz InvetoryClient. Pasaste de cliente imperativo a HTTP Interface (declarativo).

1. Antes vs ahora

ANTES — imperativo

El service arma la request

private final WebClient.Builder webClientBuilder;

webClientBuilder.build().put()
  .uri("http://localhost:8082/api/v1/inventory/reduce/" + sku,
       b -> b.queryParam("quantity", quantity).build())
  .retrieve()
  .bodyToMono(String.class)
  .block();
AHORA — declarativo

El service llama a un método

public interface InvetoryClient {
  @PutExchange("/api/v1/inventory/reduce/{sku}")
  String reduceInventory(@PathVariable String sku,
                         @RequestParam Integer quantity);
}

// en OrderServiceImpl
inventoryClient.reduceInventory(sku, quantity);

2. Cómo funciona por dentro

Vos nunca escribís una clase que implemente InvetoryClient. En WebClientConf, HttpServiceProxyFactory lee las anotaciones (@PutExchange, @PathVariable, @RequestParam) y genera en tiempo de ejecución un objeto que las traduce a una request real.

↓ inventoryClient.reduceInventory("SKU-1", 3)

Analogía de obra: antes el arquitecto (el service) también ponía los ladrillos. Ahora el arquitecto firma un plano (InvetoryClient) y la cuadrilla (proxy + WebClient) lo ejecuta. Los ladrillos son los mismos.

3. Por qué se hizo el cambio

Problema del código anteriorCómo lo resuelve la HTTP Interface
URL completa hardcodeada dentro del service, armada concatenando strings. La base vive en un solo lugar (WebClientConf); la ruta, en la anotación. El service no sabe de URLs.
El service mezclaba negocio (reducir stock por item) con detalles HTTP (verbo, query params, bodyToMono, block). El service depende de un contrato Java. Es la misma idea que private final ProductService: programar contra una interfaz.
Testear era doloroso: mockear la cadena fluida build().put().uri().retrieve()... requiere un mock por eslabón. Mockeás una interfaz con un método: when(inventoryClient.reduceInventory(...)).thenReturn("ok").
Cada nueva llamada a inventory iba a repetir la misma cadena en otro lugar. Agregás un método a la interfaz con su anotación y listo.

Eso es todo el cambio. No es que WebClient fuera malo: estaba en la capa equivocada.

4. Lo que todavía no está bien

El refactor mejoró el diseño, pero quedan detalles que conviene que conozcas:

  1. localhost:8082 sigue hardcodeado. Hay Eureka en el proyecto y la config de order-service trae una sección eureka, pero order-service/pom.xml no tiene el cliente de Eureka ni load balancer. Para resolver por nombre haría falta el starter de Eureka client, un WebClient.Builder anotado con @LoadBalanced y baseUrl("http://inventory-service").
  2. El bean se llama webClientBuilder pero devuelve un WebClient, no un builder. Engaña al que lee.
  3. Typo: InvetoryClient → InventoryClient.
  4. Se arrastra WebFlux solo para un cliente bloqueante. El pom tiene webmvc y webflux, y la llamada bloquea igual. Con Spring Boot 4 / Framework 7, la alternativa natural es RestClient + RestClientAdapter: misma interfaz InvetoryClient, sin WebFlux. Tradeoff: cambian las excepciones del catch (WebClientResponseException → HttpClientErrorException/HttpServerErrorException, WebClientRequestException → ResourceAccessException).
  5. Todo 4xx/5xx se reporta como "stock insuficiente". Un 500 de inventory no es falta de stock. Convendría distinguir por código de estado.
La lección La HTTP Interface no reemplaza al cliente HTTP: lo esconde detrás de un contrato. Por eso podés cambiar WebClient por RestClient tocando solo WebClientConf, sin que OrderServiceImpl se entere. Eso es exactamente lo que buscás cuando separás capas.
